# Решения до старта разработки

Документ фиксирует конфликты между `docs/context/02_architecture.md`,
модульными ТЗ и уже существующей обсерваторной системой. Пока пункт не
пересмотрен явно, команда следует решениям ниже.

## 1. Два «Диптиха» — два контура, одно ядро

| | №3 Настольный помощник | №8 Обсерватория |
|--|------------------------|-----------------|
| Код | Этот репозиторий | Отдельный проект Diptich_hub |
| Транспорт к ядру | MQTT `astroc/devices/desktop_diptych/#` | REST (+ webhook), адаптер в `backend/app/integrations/observatory/` |
| ESP32 | T-Panel / ReSpeaker / RFID — наши | MCC-1, Vizor-*, T-Connect — не копируем |
| БД | PostgreSQL ядра | MongoDB обсерватории (не трогаем) |

Ядро **не** управляет моторами купола напрямую и **не** поднимает второй MQTT-неймспейс обсерватории. Команды `open_dome` / `slew` идут только через API №8. Аварийные ограничения (ветер, дождь) остаются у обсерватории; ядро может лишь запросить «безопасную парковку».

## 2. Голобоксы: Windows + Unity, не Raspberry Pi

`02_architecture.md` указывает RPi 5 для Малого и Большого Голобокса.
Модули `01_maly_golobox.md` и `02_bolshoy_golobox.md` — Windows 11 kiosk,
Unity URP/HDRP, GPU (RTX 3060 / 4080).

**Решение:** следовать модульным ТЗ. RPi не обеспечивает 4K HDRP и работу
прозрачного экрана с 3D. В репозитории — HTTP/MQTT-контракт
(`clients/holobox/`), Unity-проект — отдельно.

Агент на ПК голобокса: тонкий клиент (C# в Unity или Python-sidecar),
heartbeat в MQTT, команды запуска разделов.

## 3. Home Assistant не является оркестратором

Первая половина `modules/03_diptih.md` описывает HA + ESPHome + Ollama + Whisper
как «мозг» аудитории. Архитектура ядра — FastAPI + MQTT + Celery.

**Решение:**

- Оркестрация сценариев, прав доступа и расписания — только ядро FastAPI.
- Железо терминала берём из модуля: T-Panel S3, ReSpeaker, RFID, динамик.
- STT/TTS — сервисы рядом с ядром (Vosk или Whisper; Piper; Yandex — опция).
- LLM (Ollama) — **после** MVP, за флагом `LLM_ENABLED`. В MVP — база знаний + шаблоны.
- Home Assistant допустим позже **только** как мост к свету/жалюзи, не как источник правды.

Иначе появятся два конкурирующих сценария («открыть купол» из HA и из админки)
и разъедутся роли RFID.

## 4. Речь: офлайн по умолчанию

Сеть комплекса — локальная, без обязательного интернета.

| Функция | MVP | Позже |
|---------|-----|--------|
| STT | Vosk (русский) | Whisper large, если не хватит качества |
| TTS | Piper (Дмитрий/Ирина) | Yandex SpeechKit как облачный fallback |
| Wake word | на ReSpeaker / прошивке | без отправки аудио до активации |

Голосовые записи на диск не сохраняем.

## 5. Иллюминатор: Raspberry Pi 5

Архитектура пишет RPi 4, модуль — RPi 5 4GB. Для 4K выбираем **Pi 5**.
Пульт — отдельный ESP32 (`illuminator_remote`). Плеер — VLC с аппаратным
ускорением, контент с NFS, локальный кэш 3 роликов.

## 6. Интерактивная тумба: 32", не 72"

Модуль `07_Pedestal_RFID.md` упоминает 72" — это пересечение с Большим Голобоксом.
`02_architecture.md` и глоссарий: тумба с экраном **32"**, RPi 5, RFID.
**Решение:** 32" + RPi 5. При другом железе обновить только этот ADR.

## 7. Астровизор vs Vizor обсерватории

Уличный киоск (механика NEMA + ESP32 `astrovizor_gimbal` + RPi) **не** заменяет
Vizor-1/2/3 в куполе. Ориентация телескопа запрашивается у API №8 (или MQTT-мост
обсерватории, если его дадут). Ядро транслирует Az/El киоску; парковка по ветру —
локально на киоске, дублируется сигналом от обсерватории.

## 8. Два MQTT-брокера

Обсерватория уже использует Mosquitto (возможно MQTTS). Ядро поднимает **свой**
брокер для комплексов 1–7. Мост между брокерами не делаем в MVP: статусы №8
приходят REST poll + webhook.

Если позже понадобится низкая задержка телеметрии купола — отдельный
`observatory_mqtt_bridge` с явным маппингом топиков, без слияния ACL.

## 9. Контент: NFS для видео RPi, HTTP для Unity и CMS

- Иллюминатор / тумба / Астровизор: NFS `/media/content`.
- Голобоксы: HTTP-манифест + AssetBundles (как в модулях), не NFS-монтирование Windows.
- Метаданные (название, возраст, сценарий) — PostgreSQL. Бинарники в git не храним.

## 10. Имена в коде — английские, однозначные

В коде и MQTT **не** используем слово `diptych` без уточнения:

- `desktop_diptych` — комплекс №3
- `observatory` — адаптер комплекса №8

В UI по-русски: «Настольный Диптих» и «Обсерватория».

## 11. Git

Ветки: `main` (релизы), `develop` (интеграция). Фичи — от `develop`.
Секреты только в `.env`. Первый коммит репозиторий ещё не содержит — его
нужно сделать осознанно после ревью этой структуры.

## 12. Что сознательно откладываем за MVP админки

- Управление светом/жалюзи через HA
- Захват движений на Большом Голобоксе (модуль: 2027+)
- Полноценный LLM-гид
- Полевая установка Астровизора (механика + IP65) — после стабильного ядра
- Дублирование админки обсерватории (NINA, Modbus-анализатор, OTA купола)
